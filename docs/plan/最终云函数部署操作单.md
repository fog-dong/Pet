## 0. 先决定：这次到底要不要部署云函数

**2026-11-03 制作人拍板（决策-6d）：本版只启用自建 HTTP 通路 `https://pet.jiangker.cn`，本单整体不执行；13 个云函数与 `CLOUD_ENV` 作为备用保留。** 所以除非后续改走云开发，下面 §1 起全部跳过——但请保留本单，改主意时它就是执行入口。

拍板依据（本轮实测）：`server/src/handlers/claim_habitat.rs` 已实现 `/api/claimHabitat`，定价与云函数 `claimHabitat` 逐条一致（`COINS_PER_PET_HOUR=4`、`MAX_HOURS_PER_CLAIM=6`、`MAX_DAILY_CLAIMS=2`、领养只数上限 20、超限返回 `1003 RATE_LIMITED`），铸币函数在 HTTP 侧已经成立，不依赖云函数。

客户端有两条后端通路（详见《微信后台域名配置清单》第 1 节），**部署动作取决于你选哪条**：

| 选择 | 需要做的事 | 影响 |
|---|---|---|
| **只用 Axum HTTP 自建后端**（本版采用） | 本单**整体跳过**，改按 `deploy/README.md` 核对容器 | 13 个云函数一个都不部署；小屋离线收益由 `/api/claimHabitat` 结算（已验证与云函数同价） |
| **只用微信云开发** | 按本单全做，且必须把真实环境 ID **写进源码常量 `CLOUD_ENV`**（运行时 `wx.setStorageSync` 的覆盖位不会进提审包） | 不需要配合法域名，`wx.cloud` 免校验 |
| **两条都部署** | 按本单全做 | 运行时 **HTTP 优先**（`EnvConfig.isCloudEnabled()` 先看 `resolveApiBase()`），云函数成为冷备；**风险：两套后端各记自己的 `habitat_state.lastClaimAt`，同一账号混用会让离线收益起算点错乱**，所以不建议 |

**注意 `claimHabitat` 是铸币函数**：只有它跑起来，小屋「离线收益」才为真。未接通时客户端绝不计币（红线 G4），所以这条通路要么完整可用，要么保持关闭——本版由 HTTP 侧承接。

## 2. 建库：18 个集合（顺序与索引以《云端控制台配置手册》§1 为准）

云开发控制台 → 数据库 → 新建集合，**按下表顺序**逐个建：

```text
1 users            2 hospital_state   3 pets_cases      4 pets
5 adoptions        6 ad_events        7 orders          8 config
9 leaderboard     10 assist_logs      11 delivery_logs  12 assist_pairs
13 assist_daily   14 track_events    15 ad_daily       16 sync_pending
17 habitat_state  18 habitat_claims
```

- **权限统一**：每个集合 → 权限设置 → **所有用户不可读写**（自定义规则里不放开任何客户端直读写；数据只经云函数访问）。18 个都要点，漏一个就是一个直读口子。
- **索引**：按手册 §1.3 逐条建，规则是先普通索引后唯一索引，新环境建唯一索引时集合为空所以不会冲突。
- **顺序不能换的三处**：`pets` 先于 `adoptions`；`ad_daily` 先于部署 `adEvent`；`habitat_state` + `habitat_claims` 先于部署 `claimHabitat`。
- `config` 建完集合还要**插入病例与画质配置记录**（`configKey="cases"` / `"quality"`，与 `assets/bundles/cases/config/*.json` 同构），否则 `getConfig` 返回空对象、客户端只能用本地兜底。

## 3. 上传 13 个云函数（顺序 = `DEPLOY_ORDER`，逐个右键）

| # | 函数 | 为什么在这个位置 |
|---|---|---|
| 1 | `login` | 其余函数都依赖 users 与 openid 初始化 |
| 2 | `getConfig` | 客户端启动即拉配置 |
| 3 | `saveGame` | 存档主路径 |
| 4 | `syncCaseResult` | 结算（当前为契约骨架） |
| 5 | `leaderboard` | 榜单读取 |
| 6 | `assist` | 助力：`index.js` + `settle.js` 同目录，整目录上传 |
| 7 | `adEvent` | 广告幂等记账：同样带 `settle.js`，且 `ad_daily` 必须已建 |
| 8 | `createOrder` | 固定 `3002 PAY_UNAVAILABLE`（iOS 支付占位口径） |
| 9 | `payCallback` | 同上 |
| 10 | `getProfile` | 只读当前 openid 资料 |
| 11 | `trackEvent` | 埋点落库，放业务函数之后 |

**依赖**：13 个函数只依赖 `wx-server-sdk`（^4.0.2），无其他包；若选「云端安装依赖」则本地不必 `npm install`。

## 4. `pendingMonitor` 的定时触发器（最容易被漏的一步）

CLI 与「上传并部署」**都只传函数代码，不带 `config.json` 里的定时触发器**。所以：

1. `pendingMonitor` 上传完成后，**再次右键该目录 →「上传触发器」**；
2. 到云开发控制台 → 云函数 → `pendingMonitor` → 触发器，确认列表里出现每日 09:00 的定时器，状态为「开启」；
3. 点「云端测试」手动跑一次，能返回积压统计即算装好。

其余 12 个函数**都不要**上传触发器——本项目只有 `pendingMonitor` 使用定时触发器。

## 6. 部署后验证

- **逐函数入参与期望返回**：照《W7-云函数部署操作单》§4 的表格在控制台「云端测试」逐条执行，共 22 行，含 `assist` / `adEvent` 的并发用例与 `claimHabitat` 的四类边界（连点不二次铸币、同日第 3 次 `1003`、非法入参 `1002`、取不到 openid 时 `1001`）。
- **`login` 返回值必须没有 `openid` 字段**：只允许 `token / isNewUser / serverTime / minVersion`。出现 `openid` 即为泄露，立刻回滚该版本。
- **客户端联调**：把真实环境 ID 写进本地覆盖位（不改源码、不提交）：

```js
wx.setStorageSync('pet_cloud_env_v1', '<真实云环境ID>')
```

然后依次验证：登录进大厅 → 结算一局 → 排行榜有自己 → 看一次激励视频拿到奖励 → 小屋「离线收益」能领且**连点第二次显示「毛孩子们还在休息」**。
回滚：`wx.removeStorageSync('pet_cloud_env_v1')`。
