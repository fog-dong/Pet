## 2. 替换正式 AppID（本地下发，产物注入，仓库模板不动）

> 正式 AppID 已在 2026-11-02 下发（值记在本地备忘，不写进本单）。当前状态：根 `project.config.json`（**已被 `.gitignore:32` 忽略，不落库**）已填该 AppID，构建脚本会自动把它注入产物；`build-templates/wechatgame/project.config.json` 仍是 `touristappid` 模板。

1. **注入方式（推荐，已实测）**：直接用统一构建脚本，它在构建成功后自动补注入 AppID。
   ```bash
   npm run build:wechat -- --platform=wechatgame
   # 末尾两行：appid applied to build/wechatgame-release/project.config.json
   #          build ok: wechatgame-release, launchScene=Boot 0b556a8f-…
   ```
   AppID 取值顺序：环境变量 `WX_APPID` > 根 `project.config.json` 的 `appid`。两者都拿不到时脚本只提示「appid 未注入（保留 touristappid）」并继续构建，**不会**失败——所以必须核对下面第 3 条。
2. **单独补注入**（产物已构建、只想换 AppID 时）：`npm run wx:appid -- build/wechatgame-release`。
3. 核对：`grep -o '"appid": "[^"]*"' build/wechatgame-release/project.config.json` 必须是正式值，且 `grep -c touristappid build/wechatgame-release/project.config.json` 为 `0`。
4. **不得把正式 AppID 写回 `build-templates/` 提交**：该模板是提交物，一旦写入就进公有仓库历史（`AGENTS.md` §1 第 6 条 / §6，W8 架构质检 B1 的修复项正是为此）。`build/` 整体在 `.gitignore` 中，产物不提交。
5. 不要用 `--build "appId=<正式AppID>"` 这条路：Creator CLI 的该参数**实测不生效**，产物仍写入编辑器占位 appid（记录见《W2-收口报告》§4 第 4 条），所以本项目改用「模板覆盖 + 构建后注入」。
6. 正式 AppID 注入后，在开发者工具点「预览」生成二维码真机扫码（不是「真机调试」；游客 AppID 不能生成预览二维码，这是平台限制）。二维码加载失败时先关闭网络代理、执行 `ipconfig /flushdns`；仍失败则降级到稳定版开发者工具（如 1.05）。分包体积实测（2026-11-02 release 产物，按文件字节累加）：`art` 1450 KiB、`ui` 1065 KiB、`cases` 24 KiB，主包 3423 KiB，单个分包远低于 2 MB 上限，不会触发分包加载超时，排除此项干扰；完整排查顺序见《W8-真机预览操作单》§4。

## 4. 微信开发者工具内操作

### 4.0 端到端依赖链（五段，严格按序，不可并行）

```
① 建集合与索引  →  ② 改 EnvConfig（填真实云环境 ID）  →  ③ 填广告位 ID
        ↓                        ↓                                  ↓
   18 个集合先建好         重新构建 + 上传云函数             重新构建（AdConfig 打进包）
   权限全关客户端直读        （② 必须在 ④ 之前：本地环境 ID 不影响云端，但冒烟要它）
                                                                     ↓
                                              ④ 上传 13 个云函数（顺序见 §4.2）+ login 配 SESSION_SECRET
                                                                    ↓
                                              ⑤ 上传体验版 → 真机冒烟 → 提交审核
```

| 段 | 动作 | 为什么必须在这一步 | 提前做的后果 |
|---|---|---|---|
| ① | 云开发控制台建 **18 个集合**（清单见《数据库初始化清单》/《W7-云函数部署操作单》§2.4），含 `ad_daily`、`sync_pending`、`habitat_state`、`habitat_claims`；权限统一「仅创建者可读写」→ 实际按冻结口径改为**客户端全部关闭直读直写**；建 `leaderboard` 的 `uniq_type_period_openid` 唯一索引 + `idx_type_period_score` 组合索引 | 云函数事务内读改写这些集合，集合不存在时事务直接失败，且不降级 | 结算返回 `2002`、广告计数写入报错、领取离线收益报系统错、积压监控恒空 |
| ② | `assets/scripts/config/EnvConfig.ts:8` 的 `CLOUD_ENV = CLOUD_ENV_PLACEHOLDER` 改为真实环境 ID，**然后重新构建** | `isCloudEnabled()` 判占位为 false → `Net.ready=false`，全部云端链路短路走本地兜底 | 表现是「什么都不报错但云端没通」：`claimHabitat` 永不请求、结算只进本地补发队列、排行榜恒空——最容易误判成代码 bug |
| ③ | `assets/scripts/config/AdConfig.ts:11-19` 的 7 个 `AD_UNIT_PLACEHOLDER` 换成流量主后台的真实广告位 ID，**然后重新构建** | `isAdConfigured()` 判占位为 false → `net/Ad.ts` 直接返回 `AD_UNAVAILABLE`，`AdGateway` 不发奖也不消耗当日次数 | 填一个假 ID 只会让 wx 接口报错，并绕过「占位期不降级发奖」的保护 |
| ④ | 按 §4.2 顺序上传 13 个云函数；`login` 所在环境先配好 `SESSION_SECRET` 环境变量 | `login` 缺该变量抛 `SESSION_SECRET_MISSING`，其余函数都依赖它签发的会话 | 云端全链路 1001；`pendingMonitor` 忘记「上传触发器」则每日 09:00 定时不生效 |
| ⑤ | 开发者工具「上传」→ 体验版真机跑 §3.5 的 D1–D3 → 后台提交审核 | 提审包必须是 ②③ 都已重建的产物 | 用占位包提审：审核期点开广告位/协议会命中占位态，被按「功能不可用」驳回 |

> 唯一允许调换的是 ③ 与 ④ 的先后（广告位 ID 不参与云函数依赖）。① 必须先于 ④，②③ 必须先于 ⑤ 的那次构建。

## 4.1 上线后冒烟（结算链路）

1. 用测试账号完整打一局并进入结算页，回大厅。
2. 云开发控制台 → 数据库 → `pets_cases`：应新增 1 行，`_id` 为 `openid:caseSessionId`。
3. 数据库 → `users` → `resources.coins`：应增加且只增加一次；再次进入该局（同 `caseSessionId` 重复上报）不应二次入账。
4. 若金币没有增加：先查 `config` 集合 `configKey='cases'` 是否有 `status='active'` 的文档 → 再查云函数日志里 `[syncCaseResult] reject code=2002` 是否有记录 → 最后看客户端本地下发队列（大厅底部「有 N 局结算待同步」提示是否出现）。
5. 出现「有 N 局结算待同步」属预期：配置补齐后启动/进厅自动补发，不需要玩家手动点。
