## 1. 引擎实测事实（与指令前提不一致处，先说明）

指令里的两条前提经引擎源码与构建产物核对后不成立，因此没有按前提执行：

| 指令前提 | 实测结论 | 证据 |
|---|---|---|
| 「Canvas 适配策略可能是 EXACT_FIT 拉伸，改成 Fit Width」 | 项目实际已在用 **Fit Width**：构建产物 `screen.designResolution.policy = 4`，而 `4 = ResolutionPolicy.FIXED_WIDTH`，不是 `EXACT_FIT(0)`，本来就不产生非等比拉伸，无需「改后」 | `build/wechatgame-release/src/settings.json` 的 `screen` 字段；枚举表 `cocos/ui/view.ts:909-951`（`FIXED_WIDTH=4`）、`view.ts:885`（`ContentStrategy.FIXED_WIDTH = new FixedWidth()`） |
| 「关掉 exactFitScreen 即可避免畸变」 | 该开关在**微信小游戏平台完全被忽略**：小游戏的 screen-adapter 初始化只登记回调、`windowSize` 恒等于全屏；只有 web 适配器读取它。所以改这个值对本项目目标平台没有任何效果，本轮不动它 | `pal/screen-adapter/minigame/screen-adapter.ts:166-169`、`:73-88`；web 侧 `pal/screen-adapter/web/screen-adapter.ts:329`、`:276-281`；native 注释「only works on Web platform」 |
| （补充）为什么竖屏下宽度不溢出 | FIXED_WIDTH 是单一等比缩放：`scale = 窗口宽 / 设计宽`，`_visibleRect = viewport / scale`。所以**可视宽度恒等于设计宽 1280，高度随屏幕比例变大**；横屏 16:9 是 1280×720，竖屏则是 1280×2276 甚至 1280×2773 | `view.ts:871-879`（FixedWidth.apply）、`view.ts:733-748`（_buildResult）、`view.ts:464-475`（visibleRect 取设计单位）、`view.ts:353-356`（getVisibleSize 返回 visibleRect） |
| （补充）Canvas 会不会自己撑满屏 | 运行期 `cc.Canvas` 不写 UITransform，只调相机正交高；真正把 Canvas 拉到 visibleRect 的是它自带的四边 Widget | `cocos/2d/framework/canvas.ts:123`、`:158-161`、`:213-224`；`cocos/ui/widget.ts:41-51`、`:904`；`assets/scenes/Boot.scene` 与 `assets/scenes/Lobby.scene` 的 Canvas Widget `_alignFlags=45`（上下左右全对齐、余量 0）、`_alignMode=2`（ON_WINDOW_RESIZE） |
| （补充）设计分辨率原来存在哪 | 工程本地 `settings/v2/packages/project.json` 只有 `{"__version__":"1.0.5"}`，即 1280×720/policy4/exactFitScreen=true 全部来自编辑器默认 profile，**不在版本控制里**，换机器开工程就会漂 | 改动前的该文件内容；作者路径为 `general.designResolution`，官方样例同结构：`<Creator>/resources/templates/taxi/settings/v2/packages/project.json` |

## 4. 代码侧改动清单

### 4.1 新增唯一入口 `assets/scripts/ui/ScreenMetrics.ts`（31 行）

| API | 语义 |
|---|---|
| `DESIGN_W / DESIGN_H` | 1280×720 兜底值，仅在 `view` 未就绪（返回 0）时使用 |

### 4.5 Widget 与 SafeArea 执行顺序复核（未改代码）

- 引擎 `SafeArea` 用 `@requireComponent(Widget)`，取不到同节点 Widget 时 `updateArea()` 直接 return；`updateArea` 会用 `sys.getSafeAreaRect()` 覆写 widget 的四边偏移。
- `ui/SafeLayout.ts` 的 `attachSafeArea()` 顺序为「补 UITransform → 取/加 Widget 并四边对齐 0 → `addComponent(SafeArea).updateArea()`」，即 **Widget 先、SafeArea 后**，符合引擎要求；隐私弹窗（`ui/PrivacyDialog.ts:99`）、关于面板（`ui/AboutPanel.ts:36`）、启动页合规行（`core/Boot.ts:95`）三处入口都走它。
- 结论：本轮不需要补挂 Widget，需要修的是它们父级遮罩的尺寸（§4.2）——遮罩按 720 高时，面板被安全区收进的是「一个错误的容器」。
- 一个必须说清的边界：`attachSafeArea` 给面板加的是四边对齐、余量为 0 的 Widget，引擎会按安全区**覆写面板 UITransform 的尺寸**（`cocos/ui/widget.ts:795` `updateAlignment()`，左右/上下同时对齐即构成 stretch，见 `:968-971`、`:979-981` 记录 `_originalWidth/_originalHeight`），而背景矩形是 Graphics 按 `panelW()/panelH()` 画好后不会重绘。所以 `panelW()/panelH()` 管的是「画出来的白底与内容度量」，不是那个被撑大的节点框；这正是《架构质检-W9》§八 最后一条真机观察点继续成立的原因。

## 5. 待决策：是否切换到竖屏设计帧（不在本轮自行拍板）

> 2026-10-30（W11-3）已选定 **A**：设计帧改 720×1280，落地与复核见 `docs/plan/W19-竖屏适配记录.md`。本节保留为决策依据；设计帧取值与布局口径以新文件为准，本节下表不再更新。

代码只把「同帧下的正确性」修好了。若把设计帧换成竖屏，`fitWidth` 会立刻把面板压窄，而玩法屏的横向布局并不是按 720 宽设计的：

| 位置 | 现状绝对偏移 | 720 宽帧下会怎样 |
|---|---|---|
| 弹窗双按钮 `buttonX()` | 公式给出 30 | 两枚 320 宽按钮几乎完全重叠 |
| `game/TreatmentLayout.ts:42-44` | `x=-560` | 直接超出可视宽（±360） |
| `game/Auscultation.ts:48` | `x=440` | 超出 |
| `game/DiagnosisHud.ts:14`、`game/DiagnosisLayout.ts:29` | `x=-430` | 超出，且与微信胶囊冲突 |
| `game/CaseIntro.ts:37,42` | `x=-160`、立绘右列 | 文案列与立绘重叠 |
| 化验/拍片配对（`game/LabView.ts`、`game/XrayBoard.ts`） | 左右两列 + 中央板面 | 需要改成上下两列，触摸判定与连线目标随之重算 |

两个互斥选项（需产品/美术拍板，口径来源冲突）：

- **A. 按冻结文档做竖屏**（`00-项目总览与执行边界.md:29` 「微信小游戏，竖屏，单手操作」、`16-美术风格资产规范与买量素材.md` 「设计分辨率 720×1280（竖屏），适配安全区」——该文档原写 750×1334，已于 W12-2（2026-10-30）按代码实际设计帧改为 720×1280）：设计帧改 720×1280，重排 Lobby / CaseIntro / Diagnosis / Lab / Xray / Treatment / Recovery / Result / Hospital / Adoption 十个屏 + 全部弹窗为纵向布局，是一个独立模块的工作量。
- **B. 改文档口径为横屏**：`game.json` 的 `deviceOrientation` 从 `portrait` 改为 `landscape`，同时修订 00/16 两份文档。代码与美术资产不动，但与已提交的美术资产规范、买量素材方向冲突。

本轮按 A/B 都未选的状态交付：现有横屏坐标全部保留，只做「不依赖帧宽」的度量收口。

## 6. 真机待验证清单（人工侧执行，本文件不声称已通过）

1. iPhone SE（16:9 竖屏，可视约 1280×2276）：隐私弹窗遮罩是否整屏压暗、遮罩外无响应；启动页两行合规文案是否贴安全区底边且不与 Home 指示条重叠。
2. Android 20:9 / 21:9 长屏（可视约 1280×2773）：同一组检查；额外确认排行榜 5 行 + 分页按钮不超出面板。
3. 平板 4:3（可视约 1280×1707）：`panelH()` 仍为 580，确认标题与按钮不重叠。
4. 刘海 / 挖孔机型：`SafeArea` 覆写后的四边余量实测（`sys.getSafeAreaRect()` 真机返回值与模拟器不一致）。
5. 诊断三小游戏（听诊/拍片/化验）拖拽：全屏图层改动后连线落点与 `toLocal` 取值是否仍与手指位置一致（触摸坐标系在长屏下是本轮唯一没动的假设）。
6. `getVisibleSize()` 首帧时序：`onLoad` 内即建 UI 的屏（Lobby 的 `sideX` 在 `start()` 取）在低端机冷启动是否拿到过小的兜底值；若出现，需要把度量取值推迟到 `EVENT_SHOW` 后。
7. 切帧实验（决策 A 才做）：把 `policy` 临时改 `FIXED_HEIGHT(3)` 对比，确认长屏下横向不溢出的判定口径。
