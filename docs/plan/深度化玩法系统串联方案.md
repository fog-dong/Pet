## 0. 一句话结论

游戏现在有**入口、没有出口**：金币/爱心/宠物只进不出（`adoptedCount` 只增不减、`petsAdopted` 永不清、草药与护理根本不存在），所以没有目标感。本方案的核心不是加五个面板，而是加**三条消耗管道 + 一条失败管道**：

- **失败管道**：诊断错太多 → 病情恶化 → 危重 180 秒倒计时 → 转院（扣口碑）。
- **消耗管道 A**：后院种草药 → 合成耗材 → 护理（剪指甲/驱虫/舒缓药膏）。
- **消耗管道 B**：小屋养大的宠物 **送养**给好心人 → 拿大额感谢金 + **释放领养位** → 再去寻访抽新宠。这是"资源获取大头"，也是长线闭环的收口。

其中 **3 项必须服务端配合、2 项在当前冻结接口下做不到**（§9），另有 **3 个已存在的代码地雷**必须先拆（§1.3）。

## 2. 全局闭环（模块五第 11 条的可执行版本）

```
寻访(100金) ──新宠──> 接诊 ──诊断(可能恶化/危重180s)──> 治疗(错药→心情↓+康复×2) ──> 康复 ──> 领进小屋
   ▲                        │                                                          │
   │                        └──失败(转院)──> 口碑↓ + 退一半药 ────────┐                  │
   │                                                                │                  ▼
   └──重复宠→50~300金+1~8心                                        │        后院种草药(2h)
                                                                    │                  │
                            金币/爱心 <── 感谢金600~2400 <── 送养审核 <── 护理(剪甲/驱虫/药膏) <── 合成
                                                                    │
                                          诊所升级(28,000金满级) <───┘
```

**三个入口、三个出口**：入口是寻访抽卡（消耗金币）与病例（产出资源）；出口是诊所升级（28,000）、耗材合成（金币+草药）、送养审核（金币或爱心）。**送养是唯一"大额产出 + 释放领养位"的双效动作**，所以它必须放在闭环末端，且数值要显著高于单局（§6.3）。

## 3. 模块一：负反馈与紧张感（第一优先）

### 3.1 配置表 `penalty.json`（新增，与 gacha.json 同目录同加载方式）

```json
{
  "version": 1,
  "diagnosis": {
    "warnMistakes": 2,
    "escalateMistakes": 3,
    "escalateStep": 1,
    "affectionPenalty": 8,
    "moodPenalty": 12
  },
  "treatment": {
    "wrongMedicineMoodPenalty": 20,
    "wrongMedicineAffectionPenalty": 5,
    "recoveryTimeMultiplier": 2,
    "retryLimit": 3,
    "retryExhaustedTo": "crisis"
  },
  "crisis": {
    "countdownSeconds": 180,
    "scope": ["Diagnosis", "Treatment"],
    "pauseOnHide": true,
    "transferRefundRatio": 0.5,
    "transferReputationPenalty": 10,
    "transferHeartsPenalty": 2
  },
  "severityOrder": ["normal", "urgent", "critical"]

```

加载器 `config/PenaltyConfig.ts`（复用 `config/ConfigLoader.ts:8` `loadConfigJson`，不新起第二套配置系统）；**缺配必须回落到上面的内置兜底常量并 `Track` 告警**，不能静默（08 §7 红线）。

### 3.2 三条规则的落地口径

**① 诊断惩罚（病情恶化）**

| 触发 | 效果 | 落点 |
|---|---|---|
| `mistakes ≥ 2` | 顶部 HUD 出现"病情恶化"警示条 + 好感 −8 | `game/DiagnosisHud.ts` 加警示态；扣好感走 `Hospital` 新方法 `subAffection()` |
| `mistakes ≥ 3` | 危急度**上调一档**（normal→urgent→critical，已在 critical 则不再升），立即启动 180 秒倒计时 | `CaseSession` 记 `effectiveSeverity`，后续 `treatmentThreshold()` 全部按升档后的值判 |
| 心情 −12 | 只在该宠物**已在小屋**时生效（`habitat.mood`）；首诊宠物没有 habitat 条目 → 只扣好感 | 见 §3.4 的空对象问题 |

同时必须先修 M3（拍片 mistakes），否则三个玩法里有一个不进惩罚口径。

**② 治疗惩罚（选错药）**

现状是"错药 = 少 1 分，重选即可，无限重试"。改为：

| 触发 | 效果 |
|---|---|
| 提交时 `medicineMatches()` 为假且确实选了药 | 心情 −20、好感 −5、**康复时长 ×2**（`plannedRecoverySeconds` 上乘系数），并给一次明确的"用药错误"结果动画而不是静默回到多选 |
| 同一局重试第 3 次仍不达标 | 不再允许第 4 次：按"治疗失败"处理，病例进入 **危重倒计时**（`retryExhaustedTo: crisis`），给最后一次抢救机会 |
| 药品消耗 | 已扣的库存**不退**（现在 `Treatment.ts:127` 是多选事务扣库存，失败路径已在 `:130` 回滚——改为错误药不回滚，这是"有后果"的核心） |

**③ 危重倒计时（180 秒 → 转院）**

设计取舍（**这条是策划视角，请制作人留意我和你的字面要求有偏差**）：

- 现状单局总时长约 40–60 秒（诊断 2 个小游戏 + 康复 20–26 秒）。如果 180 秒墙钟覆盖到康复页，玩家会被迫**在一个已经"治完了"的页面干等 2 分钟**，这是纯负体验。
- 所以 `scope: ["Diagnosis","Treatment"]`：**倒计时只覆盖"发现病情 → 开对药"这段决策时间，提交治疗成功即解除危机**；康复页不再计时。
- `pauseOnHide: true`：切后台/锁屏暂停倒计时。否则"接个电话回来宠物被转院"是**必被差评**的设计，也是微信小游戏留存杀手。
- 超时终局（新增，现在只有玩家主动 abort 一条路）：
  - 本局失败，不结算任何金币/爱心；
  - 退还 `transferRefundRatio` = 50% 的已消耗药品（向下取整）；
  - **口碑 −10**（本地 `reputation` 计数，进 `saveGame` 快照，见 §3.3）；
  - 爱心 −2（唯一的硬资源损失，量级 = 一局普通病例的进账，不致劝退）；
  - 释放床位（复用 `Hospital.freeBed()`），走 `Result` 页的失败态而不是回大厅黑屏。

### 3.3 口碑落地（不改冻结清单）

```
SaveCodec 新增字段  reputation: number（默认 0，decode 时 Math.max(0, …)）
CloudPayload.ts:48  buildSaveSnapshot() 追加  reputation: save.reputation
服务端              saveGame/validate.ts:10 已把 reputation 列为非负整数字段 → 无需改动
```

⚠️ 两处必须申报：

1. `validate.ts` 要求**非负整数**，口碑一旦被扣到负数整包快照会被判 `INVALID_PARAM`。→ 本地 `clamp(0, …)`，口碑只减到 0 为止。
2. 排行榜的 `reputation` 榜需要服务端有写入方才有意义（§1.4 / §9 B2）；`saveGame` 写的是 `hospital_state`，而 `leaderboard` 集合读的是独立文档。两者目前**不同步**。本轮先做"口碑作为本地资源 + 失败代价"，"口碑榜"排在 §9 服务端批次。

### 3.4 心情惩罚的空对象问题

`mood` 挂在 `HabitatPet`（`cache/HabitatCodec.ts:4`），而宠物**只在领养后**才进 habitat。治疗阶段的心情惩罚对首诊宠物无处可扣。三种选择：

- **A（推荐）**：首诊宠物只扣好感，不扣心情；文案改口径为"它记下了这次不舒服"。零数据结构改动。
- B：给 `habitat` 增加"临时住院条目"（未领养也建条目）——会污染 `habitatList()` 与离线收益计价（G4），不建议。
- C：把心情惩罚挪到宠物离开小屋后的下一次互动生效——延迟反馈，玩家感知不到因果，不建议。

## 4. 模块二：后院种植与草药系统

### 4.1 地块与作物配置 `garden.json`

```json
{
  "version": 1,
  "plots": { "unlocked": 2, "max": 6, "costs": [120, 240, 420, 700] },
  "water": { "minutesSaved": 20, "dailyLimitPerPlot": 2, "costCoins": 0 },
  "crops": [
    { "id": "mint",      "name": "薄荷",   "seedCoins": 40, "growMinutes": 120, "yield": 2, "tint": "#A8C3A0" },
    { "id": "chamomile", "name": "洋甘菊", "seedCoins": 60, "growMinutes": 150, "yield": 2, "tint": "#E8D48A" },
    { "id": "catnip",    "name": "猫薄荷", "seedCoins": 90, "growMinutes": 180, "yield": 3, "tint": "#B7A6D9" }
  ]

```

- 初始 **2 块已开垦 + 4 块可买**（120/240/420/700 = 共 1,480 金币开满，≈ 4 局多），符合"能立刻玩、中期有目标"。
- 成熟 120/150/180 分钟 = 玩家一天 2–3 次回访的节奏；`water` 每次省 20 分钟、每块地每日 2 次上限（防连点把 2 小时压成 20 分钟）。上限口径复用 `cache/PetQuota.ts` 的每日计数机制，不新造一套。
- 收获产出写进**已有的 `items` 字段**（`SaveCodec.ts:30` 是通用 `Record<string, number>`，`battery` 已在用）→ 草药不新增存档字段，`herb_mint` / `herb_chamomile` / `herb_catnip`。

### 4.2 计时红线（必须拍板：Q4）

种植计时**只走本地墙钟**，与已确立的红线有两处摩擦：

| 摩擦 | 说明 | 我的建议 |
|---|---|---|
| G4（离线收益必须服务端算） | G4 约束的是**金币**铸造。草药是消耗品、不直接换金币/爱心，本地计时不铸币 | 接受本地计时，但**草药不得兑换金币/爱心**（硬规则，写进代码注释与验收断言） |

| 驱虫药剂 | 模块三「驱虫」动作的消耗品 | 见 §5.2 | 后院 → 护理的直接串联 |

**闭环校验**：一次 6 块地满轮换 ≈ 30 株/2h。按每日 3 次合成上限，最多消耗 12 株换 6 个高级粮 + 3 个药膏 + 3 支驱虫——产出会**过剩**，所以地块开满不是最优解，**多余草药的唯一去处是送养加分**（§5.3 的"照护度"），避免通胀。这条我会在数值验收里做断言。

### 5.3 送养审核与替换机制（制作人点名要求）

**先把语义钉死**（这决定后面所有实现）：现有 `game/Adoption.ts` 的"领养"是**把病愈宠物领进我的小屋**；制作人模块三第 8 条要的是**把小屋里的宠物交给好心人**。两个动作方向相反，不能复用同一个入口，否则玩家必然困惑。本方案统一称后者为 **【送养】**（面板标题「好心人领养」），入口在小屋卡片上。

**流程与配置 `rehome.json`：**

```json
{
  "version": 1,
  "review": { "costCoins": 150, "orCostHearts": 5, "waitMinutes": 30, "heartSkip": 3,
              "passRate": { "minCare": 0.55, "maxCare": 0.95 } },
  "thanks": {
    "byTier": { "common": 600, "rare": 1200, "legendary": 2400 },
    "byHearts": { "common": 8, "rare": 15, "legendary": 25 },
    "affectionBonusPerPoint": 4, "affectionBonusCap": 400,
    "careBonusMultiplier": [1.0, 1.15, 1.3],
    "decayPerGeneration": 0.8, "decayFloor": 0.4
  },
  "slotRelease": true,
  "codexKeepPermanent": true
}
```

**逻辑设计（逐条对应制作人的四条要求）：**

1. **审核消耗**：150 金币 **或** 5 爱心（两条路给不同人群：肝金币党 / 攒爱心党）。提交后进入 `waitMinutes: 30` 的墙钟审核（后院同款本地计时口径），可用 3 爱心立即跳过 → 爱心又有去处了，这是审核系统对爱心经济的**回收**作用。
2. **通过率与照护度**：`passRate` 由该宠物的**照护度**决定 = 三项属性均值（`hunger/cleanliness/mood`，`HabitatCodec.ts:4`）归一到 [0,1]，映射到 0.55–0.95。**照护度差的宠物审核大概率被拒**（拒了不退费，只提示"再照顾几天"）→ 把"日常护理"从可选变成必选。这是本方案里最重要的一处正/负反馈咬合。
3. **通过后**：随机抽取"好心人"（名字池 `CopyText.rehomeAdopterNames`，8–12 个，纯本地随机、不涉真人），播放告别动画（宠物从 habitat 卡片淡出 + 感谢金飘字，复用 `ui/FloatText.ts`），发放 `thanks` 计算结果。
4. **宠物离屋 + 图鉴永久点亮**：
   - `Save.rehomed` 追加 petId → `habitatList()` 过滤（**必须先拆 M1**，否则宠物当场回屋）；
   - `petsAdopted` **不动** → 图鉴 `Save.isAdopted()` 依旧为真（`ui/CodexPanel.ts:23`），永久点亮零成本实现；
   - `adoptedCount` 改口径（**M2**）→ **释放 1 个领养位**，闭环打通。
5. **防无限刷（"替换机制"的核心）**：同一只宠物可以再次抽到 → 再次领进屋 → 再次送养。感谢金按 `rehomeCount[petId]` 世代衰减：第 2 次 ×0.8、第 3 次 ×0.64，**下限 0.4**（配置 `decayPerGeneration` / `decayFloor`）。理由：不做衰减 → 玩家囤 3 只普通宠无限刷 600 金币，经济崩；衰减到 0 → 老宠变废卡，收集党反弹。0.4 地板保证"再养一只熟宠仍然有得赚，但不如去抽新宠"，把玩家推回寻访管道。
6. **感谢金公式（可验收）**：
   `感谢金 = round( byTier[tier] × careBonus[mood档] + min(affection × 4, 400) ) × 0.8^generation`
   其中 `careBonus` 三档由送养时 `mood` 决定（<40 → 1.0 / 40–69 → 1.15 / ≥70 → 1.3，与 `claimHabitat` 的心情系数**同一套分档口径**，避免两套标准）。
   爱心 = `byHearts[tier]`（不随世代衰减——爱心是稀缺品，衰减它会削弱送养动力）。
   稀有度 tier 从 `config/gacha.json` 的 `tiers[].pets` 反查，**不在新表里重复定义 tier**（避免两处口径）。
7. **与离线收益的冲突（必须申报）**：服务端 `claimHabitat` 按 `pets` 集合 `status='adopted'` 的只数计价，**而送养只发生在客户端**（D19：habitat 不上云）。→ 送养后服务端仍按未送养的只数铸币，**离线收益不会随送养下降**。这既是一条偏差，也是"送养无损失"的隐形 buff。三个选项见 **Q3**。

### 5.4 为什么送养是"资源获取大头"

单局 3★ 复通 ≈ 350 金币 + 1–3 爱心。送养 1 只普通宠 = 600–1,000 金币 + **8 爱心**，且释放 1 个领养位（不释放就要靠 10 秒等待/广告/分享腾位）。满级 28,000 金币按送养节奏 ≈ **25–30 次送养**，比 80 局纯接诊快得多——这正是制作人要的"长线目标 + 资源大头"。

## 13. P2-A1 拍片误判真实计数 + 诊断/治疗负反馈实装记录（2026-11-04）

### 13.1 口径

- **M3 修好（拍片 mistakes 不再恒 0）**：落指到抬手算「一笔」，整笔都没靠近任何病灶才记 1 次误判；同一次长擦（验证里 14 个采样点）只加 1 次，起点在远处、中途跨过病灶的那笔因 `markNear()` 整笔作废。靠近判定沿用 `resolveLesions()` 的 `tolerance`（当前 110），与显影判定分离——显影看擦除覆盖率，误判看笔迹是否靠近过病灶。
- **误判同时进星级**：`judgeStars(mistakes, timeUsedMs, TOTAL_MS)`，白擦不只浪费时间，还拉低诊断评价（回到 §12 P1-B-2 申报的"mistakes 恒 0"偏差之前口径）。
