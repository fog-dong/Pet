## 1. 占位为什么不会被误判成「已配置」

| 开关 | 占位时行为 | 代码证据 |
|---|---|---|
| `isCloudEnabled()` false（`CLOUD_ENV = 'ENV_PLACEHOLDER'`） | `Net.init` 返回 false → `Net.ready` 恒 false → 全部调用点短路走本地兜底，不发请求、不报错、不阻塞单局 | `config/EnvConfig.ts:5`、`:16-17`、`net/Net.ts:36`；`Net.ready` 守卫 10 处代码 + 2 处注释（Profile / CloudSave×2 / AdEvent×2 / AssistSync / SyncCaseResult / AdoptionActions / LeaderboardPanel / Track） |
| `isAdConfigured(scene)` false | `Ad.showRewarded` 直接返回 `AD_UNAVAILABLE`，不调 `wx.createRewardedVideoAd`；`AdGateway` 对未配置场景不发奖、不消耗当日次数、不降级 | `config/AdConfig.ts:26-29`、`net/Ad.ts:38`、`net/AdGateway.ts:51-55` |
| `legalUrlsReady()` false | 启动自检记一笔 + Debug 警告，release 不阻塞；协议正文走 `points` 常量，不依赖 URL | `config/LegalConfig.ts:109-111`、`core/Boot.ts:129-134` |
| `customerServiceReady()` false | 关于面板直接预显示兜底文案，不拿占位 URL 调客服接口 | `config/LegalConfig.ts:104-106`、`net/Support.ts:16-17`、`ui/AboutPanel.ts:64-66` |
| `appid = 'touristappid'` | 只在开发者工具模拟器可跑，不能生成真机预览二维码（平台限制，不是代码问题） | `build-templates/wechatgame/project.config.json:15` |

另有一条容易混淆的本地文件：仓库根 `project.config.json` 已被 `.gitignore:32` 忽略，里面是开发机用真实 AppID 打开构建目录的本地配置；**它不参与构建、不得提交**。构建产物里的 appid 只来自 `build-templates/wechatgame/project.config.json`。

## 3. 替换后自检（本地可跑）

1. `grep -rn "PLACEHOLDER\|example.com\|touristappid" assets/scripts/config/` —— 只应剩占位常量定义本身（`AD_UNIT_PLACEHOLDER`、`CLOUD_ENV_PLACEHOLDER`、`PLACEHOLDER_HOST`）。
2. `grep -rn "Net.ready" assets/scripts --include=*.ts` —— 仍为 10 处代码 + 2 处注释；填入真实 `CLOUD_ENV` 后 `isCloudEnabled()` 才可能为 true。
3. `npm run build:cloud` + `tsc --noEmit` ×3（根 / scaffold / cloudfunctions）全绿。
4. Creator 构建后扫发布包：`node <临时目录>/scan-release.js build/wechatgame-release`，要求 `DebugPanel/SHOW_FPS/DebugText/wx_friend_/本地模拟/mock/SESSION_SECRET` 全 0；`AD_UNIT_PLACEHOLDER`、`ENV_PLACEHOLDER`、`example.com`、`touristappid` 在替换后也必须为 0。
5. `npm run verify:idempotency` —— 7 个用例全过（W11-4 实测，见 §5）。

## 5. W20 判定：`syncCaseResult` 幂等断言

| 项 | 内容 |
|---|---|
| 原始描述 | 《架构质检-W9》§四 W20：幂等只能断言「三次一致 + 零写入」，结算落地后需改为「只第一次发奖」 |
| 现状 | （W11-4 时状态，留作记录）云函数 `cloudfunctions/syncCaseResult/index.ts:1` 仍是 `STATUS: scaffold`，只校验入参并返回 `{ result:null, rewards:null, resources:null }`，不写库；客户端结算在本地完成（`game/CaseSettle.ts:59-76`），上报在 `game/Result.ts:95-99`；断言在 `scripts/verify-cases.js:8-29` |
| 判定 | **不能代码侧修（本轮不硬改）**，标为「待决策：结算落地排期」（历史判定；W12-3 已落地） |
| 理由 | 服务端结算要按冻结接口 §2.4 重算星级/治疗/奖励（客户端奖励字段一律忽略），需要把病例奖励配置带进云端，并以 `openid + caseSessionId` 唯一键写 `pets_cases` + `users.resources`；这是新功能而非警告修正，且会改变已冻结的写入语义 |
| 保持现状的理由 | 把「零写入」断言改成「只第一次发奖」而服务端仍不发奖，等于制造假通过；本轮保留原断言并在输出里注明骨架状态 |
| 落地建议 | 结算实现时用 `db.runTransaction` + `pets_cases` 唯一键 + 事务内写资源；断言改为「3 次调用仅第 1 次写库，后两次返回历史结果」 |
| **关闭状态** | **已关闭（W12-3，2026-10-30）**：`cloudfunctions/syncCaseResult/index.ts` 改为 `STATUS: implemented`，按 `config.configKey='cases'` 重算星级/治疗/奖励，事务内写 `pets_cases._id=openid:caseSessionId` 并只首次给 `users.resources` 入账；断言改为「三次都 code=0 且返回一致 / 只第一次发奖 / 只写 1 条」，另补二刷 `firstClear=false`、12 路并发只写一次、主键唯一阻止直写；`npm run verify:idempotency` 14 用例全通过 |
| 关闭后遗留 | 冻结入参缺 `recovery`（康复星级固定 1 星）与 `time`（治疗分只做上下夹紧），见《架构质检-W12》D13；客户端 `saveGame` 仍会用本地快照覆盖 `resources`，属《架构质检-W11》W10 既有警告 |
