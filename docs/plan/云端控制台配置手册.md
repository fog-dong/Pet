## 1. 任务一：数据库建表与索引清单

### 1.1 与你给的 10 集合表的偏差（先对齐口径，再动手）

你在需求里贴的表是 10 个集合（`users / cases / case_sessions / pets / habitat_state / habitat_claims / ad_events / orders / config / sync_pending`）。与冻结口径逐条对照，差异如下——**按下表修正后再建库，否则云函数会在事务里直接报错**：

| 你的写法 | 冻结口径 | 说明 |
|---|---|---|
| `cases` | 不是集合，是 `config` 集合里的一条记录 | 病例表走版本化配置：`configKey="cases"`、`version`、`status="active"`、`payload`（与 `assets/bundles/cases/config/cases.json` 同构）。建成独立集合会让 `getConfig` 读不到 |
| `case_sessions` | `pets_cases` | 单局记录与病例同一集合，幂等主键 `_id = openid:caseSessionId`，`caseSessionId` 唯一索引 |
| 缺 `hospital_state` | 必须建 | 医院等级/床位/房间/医生/装饰的存档，`saveGame` 事务写它 |
| 缺 `adoptions` | 必须建 | 只存领养关系（不存展示字段），图鉴按 `petId` 联表读 `pets` |
| 缺 `leaderboard` | 必须建 | 排行榜快照，`type+period+openid` 组合唯一 |
| 缺 `assist_pairs` / `assist_daily` | 必须建 | 助力幂等 + 被助力方日计数（同事务读改写） |
| 缺 `ad_daily` | 必须建 | 广告发奖日计数。**集合不存在时 `adEvent` 事务直接失败，不降级为无上限发奖** |
| 缺 `track_events` | 必须建 | 埋点批次落库，建议 30 天 TTL |
| 缺 `delivery_logs` | 必须建 | 发货与退款对账 |
| （未提）`assist_logs` | 建空集合即可 | W8 起被 `assist_pairs` 取代，只保留只读历史、不再写入；建库时一起建，避免历史查询报错 |

合计 **18 个集合**（9 核心 + 9 辅助，含 `assist_logs` 只读历史）。这与《数据库初始化清单》v1.1 的 15→18 计数一致；《集合与索引冻结》§2 数的是 17（不含只读的 `assist_logs`），两份不矛盾。

`pets` 的索引你写"按 `petId` 建唯一索引"——与冻结口径一致，但还需 `openid+status` 组合等 4 个二级索引，见 §1.3。

### 1.4 权限设置

18 个集合权限**全部一样**：控制台 → 数据库 → 集合 → 权限设置 → 选「**所有用户不可读写**」。

- 不要选「仅创建者可读写」。那条规则的语义是"客户端按文档 `_openid` 匹配当前用户"，而本项目文档主键是业务 ID（`openid:caseSessionId`、`openid_yyyy-MM-dd`），不是 `_openid`；选了它等于给客户端留了一个"能读到自己文档"的口子，与《集合与索引冻结》§6-7「客户端全部关闭直读直写」冲突。
- 云函数用服务端身份访问数据库，天然绕过集合权限，不需要为此放开任何客户端权限。
- `config` 目前也保持关闭。只有在确认要改成客户端直读配置时才放开只读，且 `payload` 里不得放价格与密钥。

## 2. 任务二：一键部署脚本（cloudbase-cli）

### 2.1 两个脚本的分工

| 脚本 | 通道 | 何时用 |
|---|---|---|
| `scripts/deploy-cloud.js`（`npm run deploy:cloud`） | 微信开发者工具 CLI（`cli.bat cloud functions deploy`） | 已装开发者工具、习惯用它的登录态 |
| `scripts/deploy-all-cloud.js`（`npm run deploy:cloud:tcb`） | cloudbase-cli（`tcb fn deploy`） | 不想开 IDE、或在 CI/纯命令行机器上部署 |

两者的**函数顺序、集合前置与本地自检来自同一份 `scripts/cloud-manifest.js`**，不会出现两套顺序。默认都是 dry-run，只打印命令；`--apply --yes` 才真正调用 CLI。**部署动作属于人工操作，Agent 不得代跑。**

### 2.2 前置：装 CLI + 登录 + 拿环境 ID

```bash
npm i -g @cloudbase/cli        # 本机实测可装到 3.8.x
tcb login                       # 扫码登录，登录态只留在本机
node scripts/deploy-all-cloud.js --detect   # 列出当前账号可见的云环境 ID
```

`--detect` 调 `tcb env list --json` 并递归收集所有 `envId` 字段打印出来；CLI 没装或没登录会直接告诉你退出码和原因（不会把命令行噪音当成环境 ID），返回 JSON 解析不了时退回按 `名字-后缀` 的形状逐行匹配。**解析到多个候选也不会自动选**——填错环境等于把 13 个函数传到别的环境上，所以必须你自己确认那一条，再填给 `--env`。环境 ID 只出现在命令行里，**不写进仓库**。

### 2.3 用法

```bash
# 1) 预演：本地自检 13 个函数 + 打印将要执行的全部命令（tcb 没装也能跑，只打印不执行）
npm run deploy:cloud:tcb -- --env 你的环境ID

# 2) 真部署（先决条件：tcb login 成功、已按 §1 建完 18 个集合、已发布 cases active 配置）
npm run deploy:cloud:tcb -- --env 你的环境ID --apply --yes

# 常用变体
npm run deploy:cloud:tcb -- --env 你的环境ID --only login getConfig   # 只重传部分函数
npm run deploy:cloud:tcb -- --env 你的环境ID --remote-deps            # 依赖交给云端 npm install
npm run deploy:cloud:tcb -- --env 你的环境ID --tcb "D:\path\tcb.cmd"  # CLI 不在 PATH
```

脚本先做一件事：`tcb env use <环境ID>` 把 CLI 的全局默认环境切到你填的环境——**本 CLI 的 `fn deploy` 没有 `-e/--env-id` 参数**，环境只能由全局默认或 `cloudbaserc.json` 的 `envId` 决定（脚本用前者，所以不往仓库里写任何环境 ID）。之后每个函数依次做两件事：

1. **装依赖**：在函数目录内跑 `npm install --omit=dev`。目录里已有 `node_modules` 时自动跳过这一步。
2. **部署**：`tcb fn deploy <函数名> --dir <函数目录> --install-dependency <true|false> --force`。

依赖有两种做法：默认把 `node_modules` 随代码包一起上传（`--install-dependency false`）；加 `--remote-deps` 改为云端安装（`--install-dependency true`）。**注意**：CLI 明确写了 Node.js 22 及以后的运行时不支持云端安装，会被静默忽略——所以只有确认运行时 ≤20 时才用 `--remote-deps`，否则函数会因为缺依赖起不来。仓库里 `cloudfunctions/*/node_modules/` 已被 gitignore，两种做法都不会把依赖提交进 Git。

本地自检会在下面四种情况下判 FAIL 并中止（不会带着坏产物去部署）：缺 `index.js`（先跑 `npm run build:cloud`）、缺 `package.json`、`index.js` 首行没有 `GENERATED from index.ts` 标记（疑为手改产物）、`index.ts` 比 `index.js` 新（产物过期）。

命令统一走 `--dir` 直连仓库目录，因此**不需要**在 `project.config.json` 里配 `cloudfunctionRoot`（本项目三处配置文件都没有它，这是之前 GUI 逐条上传走不通的原因）。

任一函数失败立即中止，不继续部署后续函数：函数之间有调用依赖，部署一半比不部署更糟。

### 2.4 部署完成后仍需人工补做

| 项 | 做什么 |
|---|---|
| `login` 环境变量 | 控制台 → 云函数 → `login` → 配置 → 环境变量：`SESSION_SECRET=<32 位以上随机串>`。缺它时 `login` 抛 `SESSION_SECRET_MISSING`，其余 12 个函数全链路 1001。**每次重传函数配置后都要复核一遍** |
| `pendingMonitor` 触发器 | CLI 不创建定时触发器。控制台 → 云函数 → `pendingMonitor` → 触发器 → 新建 timer，每日 09:00（口径见《W14-积压监控操作单》） |
| 超时与并发 | 控制台把 `syncCaseResult` / `claimHabitat` / `adEvent` / `assist` 的执行超时设到 ≥10s（客户端 `Net.call` 是 8s，函数侧先超时会出现"客户端还在等、云端已判失败"，见 §3.2）。首次部署也可用 cloudbaserc.json 的 `functions[].timeout` 带上，见下条 |
| cloudbaserc.json（可选） | `tcb fn deploy` 会读 cwd 下的 `cloudbaserc.json`，里面的 `envId` / `functions[].timeout` / `runtime` / `envVariables` 会直接生效。**脚本不依赖它**（走 `tcb env use` + `--dir`）。若你临时建一份来批量带上了超时配置，它是本机文件：**不得提交**，`envVariables` 里也不要写 `SESSION_SECRET` 之外的密钥、不要把真值留在任何进 Git 的文件里 |
| 云存储 | 音频等 `resource_manifest` 资源上传到云存储 `pet-res/` 下，并在 `config` 里发布 `resource_manifest` 的 active 版本 |

## 3. 任务三：真机测试问题排查预案

真机（微信「预览 / 真机调试」）最容易踩的三类问题，按"看到哪一行 → 改哪里"给出。开发期统一用**测试环境**，不接真实支付、不投真实广告。

### 3.1 分包加载失败

| 现象 / Console 行 | 根因 | 调整 |
|---|---|---|
| `assetManager.loadBundle` 报错，游戏停在 Boot 不进大厅 | 产物 `game.json` 的 `subpackages[].root`（本项目为 `subpackages/{ui,art,cases}/`）与实际目录不一致，或上传的不是 `build/wechatgame-*` 产物目录 | 确认开发者工具打开的是 `build/wechatgame-*` 整个产物目录；重新 `npm run build:wechat -- --platform=wechatgame` 后**必须重跑** `npm run wx:appid` 再上传 |
| 埋点里出现 `boot_cases_bundle_missing`（不是红字，是 `Track` 打的） | cases 分包没下下来，客户端已自动退回内置 2 例兜底 | 属可继续运行状态，但覆盖不到病例，要查上一步；本地兜底逻辑在 `assets/scripts/core/Boot.ts` |
| `Error: 无效的包名` / `subpackage ... not found` | 开发者工具「不校验合法域名/分包」在真机不生效，或真机跑的是旧版本包 | 真机必须重新点「预览」生成新二维码；必要时清缓存：工具栏 → 清缓存 → 全部清除 |

排查顺序：先看 Console 有没有 `loadBundle` 相关红字 → 再看网络面板里分包请求是否 404 → 最后确认上传的产物目录。**判定线**：主包 ≤4 MB、总分包 ≤30 MB（当前 release 实测主包 3423 KB / 分包 3919 KB）。

### 3.2 云函数超时 / 调用失败

| 现象 / Console 行 | 根因 | 调整 |
|---|---|---|
| `Error: errCode: -1 \| errMsg: cloud.callFunction:fail ... timeout` | 函数冷启动叠加控制台里设的执行超时太短；客户端 `Net.call` 是 8s 超时、重试 2 次，函数侧比客户端先超时就会出现"客户端还在等，云端已判失败" | 控制台把该函数的执行超时调到 ≥10s；先手动调一次暖起来或配置预置并发；确认 `game.json` 的 `networkTimeout.request` 仍是 8000（与客户端一致，改这里要同步 `Net.ts` 默认值） |
| 返回 `{code:-2,msg:"NET_TIMEOUT"}`，金币没到账但也没丢 | 客户端 8s 内没等到，已进补发队列 | 正常降级，不用改代码。启动 / 进厅 / 下局结算后会自动重试，7 天过期。想看是否积压：控制台查 `sync_pending` 集合有无该用户的 `lastCode=2002` 标记 |
| 全部函数返回 `{code:1001,...}` | `login` 的 `SESSION_SECRET` 没配或重传配置时被清掉 | §2.4 第一项；配完**重新部署一次 `login`** |
| 结算恒返回 `{code:2002,msg:"INVALID_STATE"}` | `config` 集合里没有 `status="active"` 的 `cases` 版本 | 按《人类执行手册》§2.4 发布病例配置；未发布时 `syncCaseResult` 必然 2002 |
| 事务类函数（`adEvent` / `assist` / `claimHabitat`）偶发失败，日志里 `RESOURCE_EXHAUSTED` 或 `Mongo transaction conflict` | 并发事务在同一文档上冲突，SDK 默认重试 3 次 | 不改代码：冲突会走 `hours=0` / `granted=false` 分支，不重复铸币。若频繁出现，看是否把 `count` 写成了 `inc()`——冻结口径禁止 `inc(±1)` 与"先写再回滚" |
| 权限报错 `database collection not exists` / `permission denied` | 集合没建，或权限被改成了非"所有用户不可读写" | 回 §1.2 补齐集合；`ad_daily`、`habitat_state`、`habitat_claims` 缺失时事务不会降级，直接报错 |

### 3.3 域名 / 跨域限制

| 现象 / Console 行 | 根因 | 调整 |
|---|---|---|
| `request:fail url not in domain list` | 开发者工具勾了「不校验合法域名」，真机不认这个勾。所有 `wx.request` 的域名必须在小程序后台「开发设置 → 服务器域名」的 request 合法域名里 | 本项目**联网只走 `wx.cloud`（callFunction / downloadFile），正常不会出现这条**。一旦出现，说明有代码绕过了 `net/Net.ts` 直接发 HTTP——按 AGENTS §1-3 这是违规，应改回云函数调用，而不是去加白名单 |
| 云存储资源（音效/贴图）拿不到，`CloudResCache` 返回 null（表现为图占位、音效静音，不崩溃） | `wx.cloud.downloadFile` 的 `fileID` 路径写错，或云存储里根本没上传该文件；也可能是 `config` 的 `resource_manifest` 与实际文件对不上（`md5`/`size` 校验不过会被判失效） | 控制台云存储里按 `pet-res/...` 核对文件是否存在 → 核对 `resource_manifest` 的 `key/md5/size/version` → `downloadFile` 超时看 `game.json` 的 `networkTimeout.downloadFile`（当前 500000ms，大文件不要缩短） |
| `cloud.init` 相关报错：`env not found` / `Invalid environment` / `Cloud API isn't enabled` | `wx.cloud.init({env})` 的 env 与当前小程序或当前账号不匹配；或在环境还没解析出来时就去调了 `callFunction` | 确认 `assets/scripts/config/EnvConfig.ts` 里的 `CLOUD_ENV` 是本小程序自己的环境 ID，**改完必须重新构建**（这行和主包在一起，没有热更通道）。调试期可用本地覆盖位 `wx.setStorageSync('pet_cloud_env_v1','<环境ID>')`，但提审包必须是源码里的那一行。客户端侧已把"未 init 就调用"按断网处理（`{code:-1,msg:"NET_NOT_READY"}`），复现时检查调用方有没有先判 `Net.ready` |
