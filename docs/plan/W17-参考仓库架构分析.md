## 一、board-game Server 架构摘要

### 1.1 语言与框架

| 维度 | 事实 |
|---|---|
| 语言 | Rust 2021 |
| Web 框架 | Axum 0.7（`json` / `macros` / `ws` / `multipart`） |
| 异步运行时 | Tokio（`full`） |
| 数据库访问 | SQLx 0.8（`runtime-tokio` + `postgres` + `chrono` + `json`） |
| 鉴权 | `jsonwebtoken` 9，JWT HS256，30 天过期 |
| 其他 | `dashmap`（内存房间通道表）、`tokio::broadcast`（房间内广播）、`reqwest`（微信接口）、`tracing`（日志） |

入口 `server-rust/src/main.rs`：读取环境变量 → 连接 PostgreSQL → 启动时自动执行 `sqlx::migrate!` → 组装 `AppState` → 注册路由 → 监听 `0.0.0.0:3000`。

### 1.2 数据持久化

PostgreSQL 单库，核心 6 张表（`server-rust/migrations/001_init.sql`、`002_content_security.sql`）：

| 表 | 作用 | 关键设计 |
|---|---|---|
| `app_user` | 用户与累计战绩 | `open_id` 唯一；`coins` / `games_played` / `wins` 计数字段；`profile JSONB` 存扩展资料 |
| `uno_room` | 房间元信息 | 6 位 `room_code` 唯一；`status` 0=等待 1=对局中 |
| `uno_room_seat` | 房间座位（4 座） | `(room_id, seat_no)` 唯一；`is_bot` 标记 AI 补位；`user_id` 可为空 |
| `game_session` | **牌局全量快照** | 每房间一行，`state JSONB` + 单调递增 `version` |
| `user_event` | 行为总线上报 | 客户端时间与服务端时间分离 |
| `media_check_task` | 头像异步内容安全 | 图片先落 BYTEA，微信异步判定，`risky` 后停止对外提供 |

关键模式：**权威状态整体序列化为 JSONB，读写都在事务内 `SELECT ... FOR UPDATE`，每次落库 `version = version + 1` 并 `RETURNING version`**（`handlers/game.rs` 的 `load_game_tx` / `save_game_tx`）。客户端只消费视图，不直接合并状态。

### 1.3 实时通信

双通道并存：

1. **WebSocket**（`handlers/ws.rs`）
   - 大厅：`GET /ws/uno/room?room_code=`，首帧推送房间快照，后续广播座位变化。
   - 牌局：`GET /ws/uno/game?room_code=&token=`，首帧推送 `GameView`，之后只推 `{"t":"game","version":N}` 这类**轻量 tick**，客户端凭 version 再拉接口取最新视图。
   - 每 20s 服务端发协议 Ping，规避反代 60s 空闲断连。
   - 鉴权优先 `Authorization: Bearer`，微信 `connectSocket` 自定义头不稳定时允许 `?token=` 兜底。
2. **HTTP 轮询/快照**：`GET /api/uno/room/detail`、`GET /api/uno/game/view`，作为 WS 不可用或补拉兜底。

广播实现 `realtime.rs`：`DashMap<room_id, broadcast::Sender<String>>`，进程内内存频道，容量 64；慢消费者 `Lagged` 时跳帧继续，通道关闭才退出。**该机制强依赖常驻进程，Serverless 云函数无法直接照搬。**

### 1.4 鉴权

- 登录：`POST /api/user/login`，微信 `code` 换 openid；开发模式允许本地 open_id 兜底（`DEV_MODE`）。
- 会话：服务端签发 JWT（`sub=user_id`，30 天），`AuthUser` 作为 Axum 提取器从 `Authorization` 解析，openid 不进入客户端载荷。
- 客户端兼容：每个请求带 `X-App-Version` / `X-App-Env`，handler 可用 `ClientInfo::at_least("x.y.z")` 做版本分支。

### 1.5 后台任务与一致性

| 机制 | 位置 | 作用 |
|---|---|---|
| `timeout_ticker` | `handlers/game.rs` | 每 3s 扫描；真人回合 30s 无动作 → AI 托管代打一步；落库前二次校验 `updated_at`，避免与真人动作抢牌 |
| `bot_ticker` | `handlers/game.rs` | 每 5s 兜底扫描卡在 AI 决策阶段的房间，重启/任务丢失后重新唤起 |
| bot 链 | `spawn_bot_chain` + `BotChainGuard` | 房间级 `HashSet` 去重，保证同房间只有一条 AI 链；`Drop` 守卫防异常泄漏 |
| 启动复查 | `main.rs` | 启动 15s 后跑一次存量昵称内容安全复查 |
| 快速匹配 | `handlers/room.rs` | advisory 事务锁内串行匹配，避免并发开桌/重复入座 |

### 1.6 部署

- Docker 化：`server-rust/Dockerfile` + `deploy/docker-compose.yml`，仅 API 容器，复用外部 PostgreSQL。
- CI：GitHub Actions 构建并推送阿里云镜像（`:latest` + `:commit-sha`）。
- CD：服务器只放 compose 与 `.env`，SSH 执行 `docker compose pull && up -d`；`AUTO_DEPLOY=true` 时自动。
- 健康检查 `GET /health`；对外由 HTTPS 反代终结 TLS，微信合法域名填该 HTTPS 域名。
- 迁移随启动自动执行，无需独立迁移作业。

## 二、与 Pet 云函数的差异与可借鉴点

### 2.1 形态差异

| 维度 | board-game | Pet（当前） |
|---|---|---|
| 运行形态 | 常驻 Rust 进程 + PostgreSQL | 微信云开发 Serverless 云函数 + 云数据库 |
| 状态载体 | 每房间一行 `JSONB` 快照 + version | 每用户文档（`users` / `pets_cases` / `sync_pending` 等） |
| 实时性 | WebSocket 广播 + 轮询兜底 | 无长连接；客户端 `Net.call` 请求/响应 |
| 并发控制 | 事务 + 行锁 + version 自增 | 事务 + 幂等键（如 `pets_cases._id = openid:caseSessionId`）+ 冲突重试 1006 |
| 后台任务 | `tokio::spawn` 常驻 ticker | 云函数定时触发器（`pendingMonitor` 每日 9 点） |
| 内容安全 | 异步任务表 + 微信回调 | 隐私/内容安全能力走平台接口（不在此文展开） |
| 版本兼容 | `X-App-Version` 请求头 + handler 分支 | `login`/`getConfig` 返回 `minVersion`、`forceUpdate` |

### 2.2 不能直接照搬

1. **进程内 `RoomHub` 广播**：云函数无跨实例内存与长连接，不能作为 Pet 的实时方案。
2. **常驻 ticker 轮询数据库**：Serverless 按调用计费且无常驻进程，应继续用定时触发器（如 `pendingMonitor`）。
3. **PostgreSQL 行锁**：云数据库事务语义不同，继续沿用现有事务 + 幂等键 + 重试策略。

### 2.3 可借鉴设计（按对 W17 的价值排序）

| # | board-game 做法 | 迁移到 Pet 的形态 | 用途 |
|---|---|---|---|
| 1 | **快照 + 单调 version**（`game_session.version`） | `resource_manifest` 文档带 `version`；客户端只比较版本号决定是否增量拉取 | W17 资源清单版本管理；后续存档冲突检测 |
| 2 | **首帧全量 + 后续轻量 tick** | 启动时 `getConfig` 一次性拿 manifest 摘要，运行期只比较 version，不轮询大表 | W17 非阻塞资源检查，避免拖慢启动 |
| 3 | **房间级任务去重 + Drop 守卫** | 云函数内“先抢占状态字段/幂等键，再执行”的写法，等价于 Pet 现有 `syncCaseResult` 首写幂等 | 结算/补发/资源清理类任务防并发重复 |
| 4 | **兜底巡检 ticker** | 定时触发器扫“卡住”状态（如 `sync_pending` 积压），不依赖单次调用成功 | Pet 已有 `pendingMonitor`，可扩展资源清单发布巡检 |
| 5 | **请求头带版本做兼容分支** | `Net.call` 统一附带客户端版本；配置/资源接口按版本返回不同 manifest | W17 灰度与旧版本兼容 |
| 6 | **媒体 URL 前缀 + 异步审核** | 云存储文件统一由 manifest 给出路径/URL/MD5，客户端按清单下载缓存 | W17 云存储资源管线 |
| 7 | **WS token 查询参数兜底** | 当前不涉及；若未来引入长连接，微信端需保留 `?token=` 兜底 | 预留经验，不落地 |

### 2.4 对 W17 的直接结论

1. 采用 **manifest 版本号**（对齐 board-game 的 `version` 语义），不引入 WebSocket 与常驻进程。
2. 资源清单放 `config` 集合的新 `configKey`，通过现有 `getConfig` 通道下发，避免新增接口；需同步更新冻结文档白名单。
3. 客户端以 **本地文件缓存 + MD5 校验 + LRU 淘汰** 实现“按需下载、不重复下载”，下载失败一律回退占位资源，不阻塞主流程。
4. 服务端不新增常驻逻辑；清单发布与灰度沿用 `config` 的 `status` / `grayTags` / `grayPercent` 机制。
