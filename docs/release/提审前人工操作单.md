## 2. 替换正式 AppID（本地操作，不入库）

1. 当前 `build-templates/wechatgame/project.config.json` 与构建产物均为 `appid: touristappid`（游客占位）。
2. 正式 AppID 只在本地构建时注入，例如：
   ```bash
   unset ELECTRON_RUN_AS_NODE
   CocosCreator.exe --project <工程路径> --build "platform=wechatgame;appId=<正式AppID>;startScene=0b556a8f-2609-451f-a9e7-30d58d1553da"
   ```
3. 构建后核对 `build/wechatgame/project.config.json` 的 `appid` 为正式值。
4. **不得把正式 AppID 写回 `build-templates/` 提交**；`build/` 已在 `.gitignore` 中，不提交。
5. 正式 AppID 就绪后，在开发者工具点「预览」生成二维码真机扫码（不是「真机调试」）。二维码加载失败时先关闭网络代理、执行 `ipconfig /flushdns`；仍失败则降级到稳定版开发者工具（如 1.05）。分包体积实测（2026-11-02 release 产物，按文件字节累加）：`art` 1450 KiB、`ui` 1065 KiB、`cases` 24 KiB，主包 3423 KiB，单个分包远低于 2 MB 上限，不会触发分包加载超时，排除此项干扰；完整排查顺序见《W8-真机预览操作单》§4。

## 4. 微信开发者工具内操作

> **顺序硬约束**：① 建 `ad_daily` 与 `sync_pending` 集合 → ② 发布 `cases` active 配置 → ③ 再部署 `adEvent` 与 `syncCaseResult`。顺序反了会出现「结算返回 2002、广告计数写入失败、积压监控为空」三类假故障。`pendingMonitor` 为 P2 运营监控，可随后部署，但 `sync_pending` 集合必须先建。

1. 导入 `build/wechatgame`，使用正式 AppID 与测试云环境。
   > 目录名别搞混：本节用的提审包来自上面 §2 的 Creator 命令行构建，落在 `build/wechatgame`；QA 本地校验脚本 `node scripts/build-wechat.js --platform=wechatgame` 默认落 `build/wechatgame-release`（`--output` 只接裸名，传 `build/xxx` 会套成 `build/build/xxx`）。两者都不是提交物，`build/` 整体被忽略。
2. 云开发 → 数据库：按《数据库初始化清单》建集合与索引（**含 `ad_daily` 与 `sync_pending`**；含 `pets_cases.caseSessionId` 唯一索引）。
3. **硬前置：发布病例配置**。在 `config` 集合写入 `{configKey:'cases', version:1, status:'active', payload:…}`，`payload` 与 `assets/bundles/cases/config/cases.json` 同构。未发布时 `syncCaseResult` 恒返回 `2002 INVALID_STATE`，该局不会入账；W13-2 起客户端把 2002 视为**可恢复**错误，会留在本地补发队列并在启动/进厅/下局结算后自动重试（7 天过期），因此表现为**金币延迟到账**而不是丢失。但配置发布仍是正常路径的必要条件，不能省。
4. 云开发 → 云函数：按《W7-云函数部署操作单》§3 的顺序逐个「上传并部署：云端安装依赖」（共 12 个，含 `getProfile`、`adEvent`、`trackEvent`、`pendingMonitor`）；`adEvent` 与 `syncCaseResult` 必须在本节第 2、3 步之后上传；`pendingMonitor` 部署后还需右键「上传触发器」（详见《W14-积压监控操作单》§2）。
5. 小游戏后台：选择类目（游戏，非医疗健康）、上传图标与截图、填写简介（说明虚构医疗模拟与宠物救助主题）。
6. 后台开启实名与防沉迷能力；配置隐私保护指引与客服。
7. 广告位：广告位 ID 统一收口在 `assets/scripts/config/AdConfig.ts`。提审前把 7 个 `AD_UNIT_PLACEHOLDER` 换成微信后台创建的真实激励视频广告位 ID，并回归 `extra_check` / `extra_inspection` / `accelerate` / `double_reward` / `free_slot` 五个主点位（`extra_medicine` / `extra_bed` 也需指向真实 ID）。广告位 ID 不是密钥，可以入库；AppID、环境 ID、`SESSION_SECRET` 仍不入库。

## 4.1 上线后冒烟（结算链路）

1. 用测试账号完整打一局并进入结算页，回大厅。
2. 云开发控制台 → 数据库 → `pets_cases`：应新增 1 行，`_id` 为 `openid:caseSessionId`。
3. 数据库 → `users` → `resources.coins`：应增加且只增加一次；再次进入该局（同 `caseSessionId` 重复上报）不应二次入账。
4. 若金币没有增加：先查 `config` 集合 `configKey='cases'` 是否有 `status='active'` 的文档 → 再查云函数日志里 `[syncCaseResult] reject code=2002` 是否有记录 → 最后看客户端本地下发队列（大厅底部「有 N 局结算待同步」提示是否出现）。
5. 出现「有 N 局结算待同步」属预期：配置补齐后启动/进厅自动补发，不需要玩家手动点。
