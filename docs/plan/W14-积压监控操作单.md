## 0. 这份单子解决什么

W13-2 把 `2002` 改成客户端可恢复后，积压只存在于**玩家手机的 `sys.localStorage`**，云端看不到。为了满足 W13-B「积压超 7 天会过期」的监控需求，W14-1 增加一个**服务端等价集合** `sync_pending`：

- `syncCaseResult` 返回 `2002`（病例配置未发布/病例不存在）时，写一条 `_id = openid:caseSessionId` 的标记，保留最早 `firstSeenAt`；
- 同一局后续清算成功时删除该标记；
- `pendingMonitor` 每天 09:00（UTC+8）**只读**统计：总数、剩余 TTL ≤2 天、已过期（>7 天），老化时在日志里打一行结构化 `warn`。

**覆盖边界（必须知悉）**：服务端只能看到「已经打到云函数并返回 2002」的单局；纯网络失败、事务 1006 耗尽等客户端侧重试不会产生标记。这部分仍靠客户端 `SyncBadge` 与 `pending_case_deferred` 埋点兜底。监控解决的是 W13-B 的主场景（配置晚发布），不是全量队列镜像。

## 1. 代码与集合

| 项 | 内容 |
|---|---|
| 新增云函数 | `cloudfunctions/pendingMonitor/index.ts`（无客户端调用，仅定时触发） |
| 定时配置 | `cloudfunctions/pendingMonitor/config.json`，**单触发器** `pendingMonitorDaily`，cron `0 0 9 * * * *`（7 段，秒/分/时/日/月/周/年，时区 UTC+8，即每天 09:00） |
| 新增集合 | `sync_pending`（辅助集合，字段见《集合与索引冻结》§3.9） |
| 写入方 | `syncCaseResult`（仅 2002 落标记、成功清算删除）；`pendingMonitor` **零写入** |
| 返回 | `{ code: 0, msg: 'ok', data: { total, nearExpiry, expired }, serverTime }` |
| 索引 | `sync_pending.firstSeenAt` 普通索引（`idx_first_seen`），供老化计数 |

建集合顺序：**先建 `sync_pending`，再部署 `syncCaseResult`**。集合缺失时标记写入会被 `catch` 吞掉（不影响 2002 返回），但监控会一直为空，属于「假正常」。

## 2. 部署步骤（人工执行，本单不代跑）

1. 云开发控制台 → 数据库：创建 `sync_pending`，权限关闭客户端直读直写；建 `firstSeenAt` 普通索引。
2. 开发者工具 → 云函数：右键 `pendingMonitor` →「上传并部署：云端安装依赖」。
3. **上传触发器**：右键 `pendingMonitor` →「上传触发器」。这一步必须单独做，**上传云函数不会自动让 `config.json` 的定时器生效**。
4. 验证：云开发控制台 → 云函数 → `pendingMonitor` → 测试，手动执行一次，确认返回 `code: 0` 且 `data` 三个数字存在。
5. 次日 09:05 后查看调用日志，确认定时触发已产生调用记录。

## 3. 告警配置（人工执行）

云开发控制台 →「设置 → 自定义告警」→ 新建策略：

| 配置项 | 取值 |
|---|---|
| 告警对象 | 云函数 `pendingMonitor` |
| 指标 | **云函数错误次数**（平台仅提供「错误次数」与「运行时间」两种，**不支持自定义业务指标**） |
| 统计周期 | 5 分钟（平台固定） |
| 比较方式 | `> 0` |
| 持续周期 | 2 个周期 |
| 告警频率 | 每小时一次 |
| 通知渠道 | 群告警（平台仅支持群告警，**不支持短信/邮件**） |

说明：

- 这条告警只覆盖「`pendingMonitor` 自身执行失败」（超时、权限、集合缺失等），**不覆盖积压数量**。
- 积压老化靠日志：云函数日志检索 `pending_aging`，命中行的 JSON 形如
  `{"event":"pending_aging","nearExpiry":2,"expired":1,"total":7}`；`nearExpiry`/`expired` 任一 >0 即需要人工介入。
- 策略上限 50 条，先只建这一条，避免占满配额。

## 4. 处置建议

| 日志/返回 | 含义 | 动作 |
|---|---|---|
| `expired > 0` | 已有用户积压超过 7 天，客户端会按 TTL 清掉该局 | 先查 `config` 集合 `configKey='cases'` 是否 active；再按 `lastCode` 判断是否 `2002`；修复后这些标记不会自动消失，需在控制台按 `firstSeenAt < now-7d` 手动清理（监控不写数据） |
| `nearExpiry > 0` | 有积压将在 2 天内过期 | 检查配置发布状态与 `syncCaseResult` 日志 `reject code=2002` 的 `caseId` 分布 |
| `total` 持续增长但无 `expired` | 新用户持续遇到 2002 | 优先核对 `config.cases.payload` 与 `assets/bundles/cases/config/cases.json` 是否同构 |

## 5. 优先级与节奏

- **P2 运营监控，不阻塞提审。** 即使暂时不部署 `pendingMonitor`，客户端补发链路（W13-2）仍然有效。
- 上线后第一周：每天看一次 `pendingMonitor` 调用日志与 `pending_aging` 检索结果；稳定后每周一次。
- 提审前若时间紧张，可只建 `sync_pending` 集合、延后部署监控函数；但**不要跳过建集合**，否则 `syncCaseResult` 的标记写入会静默失败。

## 6. 本单明确不做

- 不部署 `pendingMonitor`、不上传触发器、不创建告警群、不改真实云环境。
- 不让 `pendingMonitor` 删除/修改任何文档；过期标记的人工清理只走控制台。
- 不把监控结果接入客户端或排行榜。
