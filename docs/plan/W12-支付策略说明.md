## 0. 一句话结论

**在拿到游戏版号、完成微信小游戏虚拟支付签约与商户资质之前，四端一律隐藏付费入口并保持 `PAY_UNAVAILABLE`；iOS 不得用任何「长得像内购」的替代方案（伪 Midas、外部 H5、二维码、客服代充）绕过平台政策。**

## 1. 现状：代码侧的占位是完整的

| 位置 | 当前行为 | 口径 |
|---|---|---|
| `assets/scripts/net/Pay.ts:19-27` | `Pay.createOrder(sku)` 不发网络请求，直接返回 `{ code:'PAY_UNAVAILABLE', data:null }`；空 SKU 返回 `PAY_ERROR` | F1 冻结；禁止在此调 `wx.requestMidasPayment` |
| `cloudfunctions/createOrder/index.ts:46-47` | 只校验 `skuId` / `clientOrderId`，恒返回 `3002 PAY_UNAVAILABLE`，不建单、不返支付参数 | 冻结 §2.8 |

| `docs/plan/12-IAP内购与支付.md` §8 | 已写明「iOS 以官方最新政策为准，不允许则隐藏全部内购入口」 | 策略层 |
| `docs/release/占位替换清单.md` | 未登记任何支付占位项——因为支付不是「换个值就能开」，是资质闸门 | 口径一致 |

结论：**没有需要修的支付缺陷，也没有可以提前写的「半成品支付」**。W12 不动这三处。

## 2. 四端策略矩阵

| 平台 | 当前可见入口 | 当前返回值 | 政策前提 | 解锁后允许的做法 | 明确禁止 |
|---|---|---|---|---|---|
| iOS（微信小游戏） | 隐藏 | `PAY_UNAVAILABLE` | 微信官方对 iOS 虚拟支付的最新政策；Apple 3.1.1 相关约束 | 只有在官方明确开放且书面确认后才接；否则保持 IAA + 免费路径 | 伪 Midas（用 Android 参数在 iOS 拉起）、外部 H5 支付、跳转 App、二维码收款、客服代充 |
| Android（微信小游戏） | 隐藏（未配置 SKU） | `PAY_UNAVAILABLE` | 游戏版号 + 微信认证 + 游戏类目 + 虚拟支付 2.0 签约 + 商户号 | 走平台虚拟支付：服务端下单 → 平台参数 → 客户端拉起 → 回调验签发货 | 客户端传价格、客户端自行发奖、无回调即发货 |
| HarmonyOS（微信鸿蒙版小游戏） | 隐藏 | `PAY_UNAVAILABLE` | 需单独核对微信鸿蒙版是否支持虚拟支付（**当前未验证，按「不支持」处理**） | 与 iOS 同策略：未确认前只保留 IAA 与免费路径 | 沿用 Android 结论推定可用；用网页支付兜底 |
| 开发者工具 / 体验版 | 隐藏 | `PAY_UNAVAILABLE` | 无正式 AppID 与商户配置时，平台侧本就不可用 | 只允许用模拟回调跑**本地单测**，不得进发布包 | 在模拟器里伪造「支付成功」并写正式库；把 mock 支付代码提交进主包 |

> 判定规则：**平台不确定 = 按不可用处理**。宁可少一个付费入口，也不做一次违规尝试（00 §10「合规风险」为一票否决项）。

## 3. 开通前置条件（缺一不可）

### 3.1 资质与协议

| # | 前置 | 说明 | 谁负责 |
|---|---|---|---|
| 1 | 游戏版号（网络游戏出版物号） | 小游戏开放虚拟支付的前置；无版号只能 IAA | 运营 / 制作 |
| 2 | 软件著作权登记 | 版号与类目材料常见要求 | 运营 |
| 3 | 微信小游戏主体认证 + 游戏类目 | 主体、类目与版号信息需一致 | 运营 |
| 4 | 虚拟支付 2.0 协议签约 | 平台侧开通虚拟支付能力，含结算与分成条款 | 运营 + 财务 |
| 5 | 微信支付商户号 + 结算账户 | 与主体一致；退款与对账依赖它 | 财务 |
| 6 | iOS 政策书面确认 | 以平台最新公告/后台说明为准，截图留档 | 制作 |

### 3.2 工程侧（资质到位后才做）

| # | 事项 | 落点 | 验收 |
|---|---|---|---|
| 1 | SKU 与价格上云 | `config.configKey='skus'`，客户端只读 | 改价不发版 |
| 2 | `createOrder` 真下单 | 校验 SKU/价格/频控 → 建 `orders` → 返回平台参数 | 同 `clientOrderId` 重复下单返回原单 |
| 3 | `payCallback` 验签发货 | 验签 → 校验金额/openid → `transactionId` 幂等 → 事务发货 | 同回调 10 次只发 1 次 |
| 4 | `queryOrder` 查单补偿 | 回调丢失 5 分钟内补齐 | 演练通过 |
| 5 | 平台开关 | 服务端下发 `payEnabled` + 平台白名单，客户端按开关显示入口 | iOS 下开关为 false 时无任何入口残留 |
| 6 | 退款与对账 | `delivery_logs` + 每日四方对账 | 差异 24h 内闭环 |

## 4. 解锁顺序（建议，不在 W12 执行）

1. 版号 / 软著 / 类目 / 认证全部到位 → 记录政策快照（日期、判断人、结论）。
2. 虚拟支付签约 + 商户号 → 沙箱跑通「下单 → 支付 → 回调 → 发货 → 查询」。
3. 服务端先上 `payEnabled=false` 的开关与 SKU 配置（对用户不可见）。
4. 灰度：白名单账号 → 1% → 全量；每档看退款率、回调失败率、发货差异。
5. iOS 单独评审：官方未明确开放前，**永远停在步骤 3 之前**。

## 5. 现在到解锁之前，代码侧要保持的样子

- `Pay.createOrder` 不发请求、返回 `PAY_UNAVAILABLE`；`createOrder` / `payCallback` 云函数返回 `3002`。
- 大厅与所有页面**不出现**付费按钮、价格、折扣倒计时；不出现「充值」「首充」字样。
- 埋点里不采集与支付相关的设备指纹、订单意图；`Track` 现有事件表保持不变。
- 每年至少复核一次平台政策；政策变化只改本文与 `12` 号文档，不改冻结结论（F1 需制作人解冻）。

## 6. 反模式清单（任何人提都拒绝）

| 反模式 | 为什么不行 |
|---|---|
| iOS 用 Android 的 Midas 参数强行拉起 | 违反平台政策，提审直接驳回；已发生过的封号路径 |
| 用 H5 / 二维码 / 客服转账完成支付 | 站外支付，F1 明令禁止 |
| 客户端 `Pay.createOrder` 本地返回成功并发奖 | 绕过服务端校验，等于白送资源且无法对账 |
| 把 `PAY_UNAVAILABLE` 改成 `OK` 但服务端没回调 | 制造「假支付」，用户投诉与退款风险最高 |
| 在体验版/开发工具里走真实商户号 | 测试单污染对账，且违反平台测试规范 |

## 7. 与冻结文档的关系

- 本文不修改 F1 结论，只把「四端分别怎么做」写清楚；F1 的解冻需制作人书面确认并同步 `00` §16 与 `12` §8。
- 客户端接口、错误码不变：`3002 PAY_UNAVAILABLE` 仍是唯一合法返回（`接口冻结清单.md` §1.2）。
- 解锁时新增的字段（如 `payEnabled`、`orders` 状态流转）必须先改 `接口冻结清单` / `集合与索引冻结`，再改代码。
